# Скилл owner-decisions: база решений владельца

Статус: построено 10.11.2026, версия 0.1.0; живая проверка на реальной проработке фичи — впереди (#1).

## Зачем

Владелец ведёт несколько проектов через агентов и раз за разом отвечает на однотипные вопросы. Скилл хранит его ответы в общей базе и по ним решает новые вопросы-развилки, чтобы до владельца доходило только новое.

## Как работает

1. Агент в любом скилле или обычной сессии подготовил развилки для владельца.
2. До отправки вопросов он отдаёт развилки подагенту. Подагент забирает свежую базу (сам ничего не записывает), читает подходящие темы и по каждой развилке возвращает «решено» с основанием или «спросить».
3. Решённое агент принимает и записывает туда, где работа уже фиксирует решения за владельца (раздел спецификации «Решения агента — на просмотр»). Остальное спрашивает как обычно.
4. Сразу после ответов владельца агент записывает их в базу как случаи, раскладывает по темам и отправляет в репозиторий.

## Решения владельца (10.11.2026)

- Агент решает сам всё, где есть прямой прецедент, кроме денег и необратимых действий.
- Справку «как вы решали раньше» и отдельный список решённого владельцу не показывать: решённое уже видно в спецификации.
- Из истории наполнить базу немного, чтобы не тратить токены: 15 случаев из уже прочитанных записей.
- Скиллы не связаны по имени. Скилл подключается сам по своему описанию; правило в глобальном файле правил закрепляет оба момента — сверку до вопроса и запись после ответа.
- База — приватный репозиторий GitHub с md-файлами, клон в `~/.agents/decisions/`. Глобальный файл правил на другие машины владелец переносит сам.

## Хранение

- `cases/` — один файл на решение с уникальным именем (дата, проект, тема). Две машины не пишут один файл, конфликт невозможен. Случаи не удаляются.
- `topics/` — принципы по темам со ссылками на случаи и границами «где решено иначе и почему». Производные: при одновременной правке одной строки с двух машин побеждает удалённая версия, скрипт называет перезаписанную тему (`TOPIC_OVERWRITTEN`) и случаи, потерявшие место (`UNFILED`), и агент вносит свою правку заново.
- Оглавления-файла нет: список тем скрипт собирает из первой строки каждой темы.

Векторная и графовая базы не взяты: при сотнях решений подагент справляется чтением списка тем и нужной темы, а сервис пришлось бы держать и обслуживать. Вернуться к вопросу, когда случаев станет больше тысячи или подагент начнёт пропускать существующие прецеденты.

## Что считается сбоем

- Базы нет, взять её негде или скрипт завершился ошибкой — работа молча идёт как без скилла: всё спрашивается, ничего не записывается, по базе ничего не решается.
- Нет сети — работа на локальной копии, запись уходит при следующем сохранении. Причину скрипт печатает; если это не сеть, а отказ в доступе, агент сообщает владельцу одной строкой.
- Два случая расходятся и разницу нечем объяснить — один вопрос владельцу; до ответа развилки по этому принципу не решаются.
